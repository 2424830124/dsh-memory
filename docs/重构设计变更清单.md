# 重构设计变更清单

## 本轮结论

本轮包含两组工作：先对大型 `MemoryRuntime` 做功能拆分；随后按新的用户要求，加入按会话活动状态检查并合并跨会话通知。浏览器面板操作迁入独立服务，文件排序与日志注入选择成为共享/纯策略模块；通知调度器独立负责何时检查，runtime 仍负责快照 diff 与实际投递。提示词冻结、文件格式、配置和面板 API 均未改变。

| 设计点 | 改什么 | 怎么改 | 为什么 |
| --- | --- | --- | --- |
| runtime 职责集中 | 从运行时协调器移出浏览器面板的文件用例 | 新增 `lib/panel-service.js` 和 `MemoryPanelService`，集中承载概览、目标定位、文件三视图渲染、文件编辑、创建和删除；`MemoryRuntime` 保留同名方法作兼容门面，并以 `store`、共享 `config`、`resolveDirectory(scope, sessionId)`、`broadcast(directory)` 四项显式依赖构造服务 | 面板 CRUD 与提示词快照、agent 生命周期、跨会话通知策略属于不同功能。分离后面板文件用例可独立演进；显式回调避免 service 反向依赖 runtime，也不暴露或复制会话状态。旧 runtime 方法仍供 route/UI 使用，降低迁移风险 |
| 面板写入安全边界 | 保持编辑、改名和删除的原有防护 | `panel-service` 继续在文档副本上编辑；写入仍携带旧文件 `expectedHash` / `baseRelative`，改名后仍删除旧路径并同步清缓存；写入和删除后仍调用 runtime 提供的 `broadcast(directory)` 回调 | 防止提取时丢失乐观锁、改名残留文件、缓存一致性及其他会话通知 |
| 通知节奏与合并 | 从“每次变化立即检查”改为按接收会话活动状态检查 | 新增 `lib/notification-scheduler.js` / `MemoryNotificationScheduler`；写入与外部 watch 只提高目录 revision；idle 时只响应真实 user-source 消息，running 时共享 5 秒轮询（轮询间隔本身就是限流，最多每 5 秒一条提醒，不另外延迟）；`turn-stopping` 不刷队列，未检查的变更留到下一次用户消息。正常变化的快照 diff/文案/投递仍由 runtime 的 `notifyAgent()` 处理，损坏文件由 `notifyBroken()` 发独立提示。 | 多次保存不会拆成连续通知；会话结束太快时不在模型刚结束时打断/推送，而是等下一条用户消息；分离调度与 diff/inbox，避免定时策略侵入快照层 |
| 会话 revision 与并发边界 | 防止异步 diff 期间的新写入丢失 | scheduler 在调用异步 `notifyAgent()` 前捕获每个可见目录的 revision；比较完成只推进捕获到的 revision。比较过程中收到新的真实用户消息只排队一次跟进检查；running poll 与在途检查共用同一 Promise | 保证在检查期间追加的写入仍未检查；避免并发重复比较和一条用户输入触发无界重复循环 |
| 通知生命周期兼容 | 保留既有新会话、恢复、认领与丢弃规则 | 新会话以当前 snapshot 建基线；恢复会话将各目录放入私有待检查 revision；`claim()` 照旧确认快照，`release()` 除回滚基线外还释放相应 checked revision；`forget()` / `stop()` 清理 agent 状态和共享 timer | cadence 变化不应制造“新会话所有文件都是新增”、丢弃后不重发、disposed agent 泄漏等回归 |
| 文件顺序单一事实来源 | 消除注入顺序与面板排序策略留在 runtime 的耦合 | 新增 `lib/file-order.js` 导出 `orderByConfig(documents, fileOrder)`，提示词注入与面板概览共用 | 拖动排序必须与模型看到的顺序一致；策略只有一个实现点，且不依赖 runtime |
| 日志注入策略边界 | 从 runtime 提取“挑哪些日志日、哪些日包含正文”的策略 | `lib/log-injection.js` 导出 `selectLogInjection(files, rule)`；runtime 负责获取按日期升序的目录/文档对和生成快照 key，纯策略负责过滤空日、选择最近 N 天和标记详细日 | 让策略独立测试，降低 coordinator 同时承担数据获取、筛选和 key 编码的职责 |
| 日志选择重复计算 | 移除对已排序日志的二次排序及临时反向索引 | 复用 `logFilesOf()` 的升序目录/文档对；选择器的结果带回原目录，runtime 直接编码 key，不再 document→directory 映射 | 避免重复 O(n log n) 排序及额外 Map 填充/查询；行为依赖现有排序来源，未改变同日跨作用域优先级 |
| 回归验证 | 覆盖拆分后的面板和注入边界 | 在 `test/store.test.mjs` 验证 runtime 兼容入口下的面板概览、渲染、编辑/改名/新建标题/删除标题，以及文件创建、整份删除和缺失删除错误；`test/log.test.mjs` 验证策略和空日志日预算 | 确保服务委托不改变 route 使用的形状、数据落盘保护、注入顺序与日志窗口 |

## 保持不变的功能设计

- `MemoryRuntime` 仍是入口协调器；session workspace 解析仍由它持有，通过回调提供给面板服务。
- 保持不变：通知仍通过 `MemoryRuntime.notifyAgent()` 比较标题级快照并生成文案；`agent.inject()` 仍不唤醒 agent，claim/release 的快照语义保留。变化的是检查调度时机，而不是通知内容和交付语义。
- 面板的 `source`、`text`、`injected` 和 `meta/tree` 仍从同一文档和既有 render 函数派生，不让 UI 另解析 YAML 或另造注入格式。
- 注入顺序仍稳定、`fileOrder` 仍同时影响面板列表与提示词；会话冻结、快照、日志预算、空日志过滤和工作区同日覆盖规则不变。
- 没有实施自动召回、提示词顺序变更、配置/文档格式变更、跨层级移动或日志删除；没有拆动存储 cache/watch/writer 的同步机制，也未重写 UI chunk。

## 验证结果

- 六个离线 suite 逐个直接运行：`test/core.test.mjs`、`test/store.test.mjs`、`test/schema.test.mjs`、`test/log.test.mjs`、`test/settings.test.mjs`、`test/notification-scheduler.test.mjs`。
- 通知测试新增 idle 真用户边界、memory 消息过滤、活跃轮询与共享间隔、快速结束后延迟到下条用户消息、在途并发写入跟进、失败保留及 discard 释放。
- `test/store.test.mjs` 验证两次不同文件保存不立即投递，下一次用户边界生成一条同时列出两个文件的消息；恢复会话 attach 不立即通知，用户边界检查后投递；新会话发现坏文件时 attach 不立即打扰，相同错误签名只提示一次。
- 通过 `node --check`：`lib/runtime.js`、`lib/panel-service.js`、`lib/file-order.js`、`lib/log-injection.js`、`lib/notification-scheduler.js`、`index.js` 及新增/修改的测试文件。
- 旧版 `node --test` 在当前沙箱由测试 runner 创建子进程时出现 `Error: spawn EPERM`；因此直接逐 suite 运行，不能把环境限制记成测试断言失败。
